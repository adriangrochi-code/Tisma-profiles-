# Handoff — profile pack session

State of the work on branch `profiles/next` (owner's request of 2026-11-05). Kept short; update it when something
changes.

## Done

1. **Each printer's own G-code, verbatim, with its macros** (`gcode` block in model files and filaments;
   `docs/FORMAT.md`, «G-code de la máquina»).
   - Root cause of the Bambu Lab bug: Tisma Slicer's converter did not follow OrcaSlicer's `include` (per-model
     G-code templates), and it also left many other OrcaSlicer/Creality Print printers with another model's G-code.
   - The converter now reads the source programs at the commit each Tisma Slicer bundle names
     (`sources.json` → `converted_from`, fetched by `tools/fetch_sources.py`): `tools/upstream.py` resolves
     `inherits` + `include` (OrcaSlicer family) and Cura definitions + extruders.
   - PrusaSlicer-format bundles are carried as they are (`origin: bundle`).
   - Format version stays 2: the block is additive; old readers ignore it.
2. **Compatible sets:** no set is empty. Condition evaluation fixed (`num_extruders`, numbers written as strings,
   escaped new lines in notes, whole-value regex match). 392 → 50 entries fit nothing, and those fit no printer in
   their source program either: left out, listed in `stats.json` → `left_out`.
2b. **Compatible lists of the OrcaSlicer family from the source program** (inherited like any value, as
   PresetBundle.cpp does). Tisma Slicer's bundle wrote them empty (profile for every printer of the brand) or added
   printers. 2012 profiles change; validate failures 20 → 11 (the rest: layer > nozzle in the source itself).
3. **Print nozzle:** from all printers, else the condition's `nozzle_diameter[0]==X`, else the name. Printers whose
   bundle lost `nozzle_diameter` take it from the source program (3 UltiMaker 2 extended+ variants).
4. **CI check:** `tools/check_pack.py` and the converter tests (`tools/test_*.py`, unittest) (in `release.yml` before packaging, and the new `check.yml` on other branches).
5. `docs/GCODE_VARIABLES.md` (spec's gcode_macros.md rule 9): per-dialect variable tables, generated by
   `tools/gcode_variables.py` (checked by `check.yml` against the pack) from the converted pack and the source programs' definitions (PrintConfig.cpp of each
   program, Cura's fdmprinter/fdmextruder.def.json and StartSliceJob.py). Regenerate it with each new pack.
6. Release candidate: built locally, see the numbers in the last commit. The owner publishes.

7. **Key translation tables** (spec project_import.md, rule 11): `tools/translation.py` is the converter's mapping
   as data (the pack is byte-for-byte the same after the change); the pack ships `translation/<dialect>.json` in
   `translation.tar.xz`; other dialects get their PrusaSlicer names from the same presets in the source program and
   the bundle. `check_pack.py` re-translates every profile and compares.

## Open

- Variables in `orcaslicer`/`cura` G-code use the source program's names; filament and print profiles keep
  PrusaSlicer names. `gcode.values` gives the machine values with the source names. The engine's macro spec
  (spec session) must say how it maps the rest.
- Cura start G-codes set `M82` (absolute E): `gcode.relative_extrusion` is `false` there while
  `profile.settings.machine.relative_extrusion` (from Tisma Slicer's bundle, which forced `M83`) is `true`. Checked
  with engine 3667e62: with the macros it writes `M82` and absolute E, as the source; not a fault.
- 42 printers still take their G-code from Tisma Slicer's converted bundle (BlackBelt, VertexSlice, CR-30 PrintMill):
  their programs are not read, or the preset has another name there.
- Tisma Slicer kept one copy of a model that two sources have (the maker's bundle), losing the other source's
  nozzle variants (e.g. Neptune 3 Max only 0.4): their profiles are in `left_out` with `source_printers`.
- 4 groups of models share the vendor-wide base start G-code of OrcaSlicer (DeltaMaker, LONGER LK10, E3NG/VIRTU,
  WonderMaker): that is how the source has them; reported as notes, not failures.

## For the owner (Tisma Slicer, not this repo)

- `tools/profiles/convert_orca_profiles.py` (`tisma_option_types`) does not see the options PrusaSlicer adds in a loop
  over the axes (`machine_max_acceleration_` + axis, `machine_max_feedrate_`, `machine_max_jerk_`): with no type,
  their values are dropped, so every OrcaSlicer-family printer of the bundles lost its per-axis limits. The pack fills
  them from the source program; the converter in Tisma Slicer could be fixed too. Fixed on the slicer branch
  ccr-7e2013d9-qwmclz (e54d3a2); with it the pack is the same.
- The same converter does not rename OrcaSlicer's `machine_max_speed_x/y/z/e` to `machine_max_feedrate_*`: with the
  types fixed, the maximum speeds per axis are still dropped. The pack fills them by name either way.

- The same converter writes OrcaSlicer's percent options (`coPercent`: `min_bead_width`, `min_feature_size`,
  `wall_transition_length`, `wall_transition_filter_deviation`) without `%` when the OrcaSlicer profile gives a bare
  number (Flashforge AD3/AD4/Artemis: `"min_bead_width": "100"`, 100 % in OrcaSlicer); Tisma Slicer reads them as
  mm (100 mm). The pack takes a bare number over 10 as a percent.
